# Sonus 安卓版 0.3.0（测试版）

这一版让 App 更顺、更跟手，并修正一个登录问题。三件事：

- 服务器地址会跳转时（例如反向代理把 `http://` 都 301 跳到 `https://`），「在浏览器中登录」失败，提示「服务器没有开始登录（401）」。已修正。
- 测试版改用优化过的构建。
- 动效和触感按 Spotify 安卓版和 Windows 版的动效语言重新做了一遍。

## 下载

附件里的 APK 是测试版：装上后叫「Sonus 测试版」（包名 `com.creeperux.sonus.debug`，版本 0.3.0），需要 Android 13 及以上，可以直接覆盖安装 0.2.x，登录不丢。

## 修正

- **地址会跳转时，用跳转后的地址。** 以前 App 检查服务器时跟着跳转走通了，却仍记着原来的 `http://` 地址；之后发起浏览器登录的 POST 请求遇到 301，被网络库改成了不带内容的 GET，服务器回 401。现在检查服务器、用户名密码登录、浏览器登录都会改用跳转后的地址，以后的请求（包括播放和封面）也都发到那里。登录页上的地址会换成实际用的那个，所以「互联网上的 HTTP 地址」提醒也会消失。已经登录、记着旧地址的，下次连上服务器时也会自动换成跳转后的地址。
- **POST 请求不再被悄悄改成 GET。** 遇到跳转时，App 把同一个 POST（连同内容）重新发到跳转后的地址，就像 307/308 跳转那样。
- **只跟随同一台主机上的跳转。** 可以从 `http://` 升到 `https://`、换端口或路径；跳到别的主机，或从 `https://` 降到 `http://`，App 都不跟过去，也不改用那个地址（每个请求都带着登录凭证），并提示「服务器把请求从…转到了…，Sonus 没有跟过去」，不再显示让人摸不着头脑的 401。

## 测试版改用优化构建

以前发的测试版是调试构建（debug），Compose 在调试构建里明显更慢。这一版的测试版和正式版构建方式一样：

- 用 R8 压缩优化，不可调试，APK 从 46 MB 变成 5 MB；
- 带基线配置（baseline profile），安装后系统会提前编译常用代码。

它仍用同一个调试密钥签名、同一个包名，所以能直接覆盖手机上已经装的「Sonus 测试版」。

在模拟器上量了同一段自动操作的帧数据：首页上下滚动、切到音乐库滚动、打开一张专辑滚动再返回，每种各跑 3 轮。

| 构建 | 卡顿帧 | 第 95 百分位帧时间 | 第 99 百分位帧时间 | UI 线程慢帧 | 冷启动 |
|---|---|---|---|---|---|
| 0.2 的调试构建（之前发的测试版） | 3.3–3.8% | 22–24 ms | 65–89 ms | 20–25 | 0.74–0.78 s |
| 优化构建，刚装好 | 2.5–3.4% | 17–26 ms | 46–61 ms | 7–16 | 0.42–0.54 s |
| 优化构建，按基线配置编译后 | 2.2–2.6% | 16–18 ms | 40–48 ms | 3–8 | 0.48–0.51 s |
| 0.3.0（新动效），优化构建，编译后 | 1.5–1.8% | 15–19 ms | 46–48 ms | 7–8 | 0.43–0.50 s |

这是模拟器上的数字，不是真手机。在真手机上，调试构建和优化构建的差别通常更大。另外，侧载安装的 App 要等系统空闲（一般是充电、待机时）才会按基线配置编译，所以装好后头一两天可能还没到最顺的状态。

## 动效和手感

时长和缓动曲线沿用 Windows 版 `Motion.cs`：按下 60 ms、松开 120 ms、进入 140 ms、页面推入 220 ms、面板 320 ms，缓动是 cubic-bezier(.2, .8, .2, 1)。

- **播放器跟手**：
  - 迷你播放条往上拖，播放器跟着手指上来；在播放器的封面或顶部往下拖，它跟着手指下去。
  - 松手时过了三分之一，或者轻轻一甩，就完成；否则弹回原处。
  - 封面在迷你播放条和大封面之间连续变大、变小（共享元素）。
  - 点一下、返回键、左上角的收起按钮也都走同一段动画。
- **返回手势**（Android 14 及以上的预测性返回）：
  - 在页面上从边缘拖，当前页面跟着手指缩小一点、圆角变大，松手才返回，不松手就回到原样。
  - 在播放器里拖，播放器跟着往下走。
- **页面切换**：前进时新页面从右侧滑入一小段并淡入，返回时反过来，切换底部标签时淡入淡出。返回上一页会回到原来滚动到的位置。
- **页面的头几行依次出现**：专辑、歌单、首页、音乐库打开时，前几行和前几张卡片稍有先后地淡入上浮（每个间隔 24 ms，和 Windows 版一样）；往下滚出来的行不再做这个动画。
- **按压反馈**：卡片、磁贴、圆形按钮按下时缩小一点，松开时平滑回弹；以前是直接跳变。
- **播放/暂停**：图标在两者之间缩放切换。
- **点赞**：心形放大后弹回，并有一下轻微振动。
- **进度条**：按住拖动时滑块和轨道变粗；开始拖和松手时各有一下轻微振动。
- **轻微振动**：播放/暂停、点赞、把播放转到另一台设备、长按、拖动进度条。
- **长按歌曲**：打开它的菜单（和 Spotify 一样）。
- **封面**：图片淡入，不再突然出现；换歌时，播放器和迷你播放条的封面从上一首淡入下一首。列表里的封面改用更轻的加载方式，长列表滚动更省力。
- **正在播放的电平条**：只重绘、不重新排版，滚动时更省。
- **系统「移除动画」**：遵从这个设置。打开它（或把动画时长缩放设为 0）时，动画直接到终点，入场和电平条这些纯装饰的动画不再出现，和 Windows 版关掉动画效果时一样。

没有改的：

- 设备列表面板和底部提示条：它们用的 Material 3 组件本来就有进出动画。
- 底部标签栏的选中指示：本来就有动画。
- 平板的右侧面板没有加开合动画。
- 没有做全局的封面取色背景过渡：播放器背景的取色渐变原来就有（时长改成了 600 ms，和 Windows 版一致）。

## 测试情况

- 电脑上的测试：核心库和 App 单元测试 75 项全部通过，其中跳转相关的 12 项：在本机起一个小前端，把所有请求 301（以及 302、307）跳到演示服务器，检查服务器、浏览器登录（开始、批准、拿到密钥、撤销）、用户名密码登录、记着旧地址的登录自动换地址、表单 POST 都能穿过跳转；跳到别的主机、从 https 降到 http 的跳转都被拒绝、也不被采用。
- 跳转修正还没加上安全限制时，在手机模拟器上隔着一个 301 前端跑过设备测试（密码登录、浏览器登录、播放）；加上之后这部分只跑了电脑上的测试。
- 设备测试，两台静默模拟器（手机、平板）同时跑（在动效改动上跑的，还没叠加跳转修正；叠加后的设备测试还要再跑一遍）：
  - 对演示服务器：两台都是 9 项通过，各跳过二步验证那项（演示服务器没有二步验证）。
  - 对 Rust 服务器（主干编译，冻结的 Navidrome，53 首长歌的测试曲库，一次性用户）：手机 10 项全部通过（包括二步验证），平板 9 项通过（二步验证只在手机上测）。
  - Rust 上的「下一首文件丢失」那项要另起一个新曲库再跑：服务器重启后会把丢了文件的歌从列表里拿掉，测试就找不到它。新曲库上 5 项新的播放测试两台都全部通过。
- 设备测试本来就关掉了动画（`animationsDisabled`），这次没有为了动效改测试。
- 在模拟器上看过：拖动打开、拖动收起（没过三分之一会弹回）时的中间画面；改动前后各三段录屏（播放器、页面切换、按压和点赞）。

**只有真手机能判断的：**

- 手感本身：跟手拖动是否顺、振动的轻重、动画的快慢合不合适。模拟器没有振动，也不能真正用手指拖。
- 优化构建在真手机上到底顺了多少，以及基线配置编译后的效果。
- 预测性返回手势（Android 14 及以上，用手势导航时）：模拟器上只用返回键试过，没有用边缘滑动手势试过。
