# R2 镜像设计（阶段 5 最后一部分，决定 6）

2026-11-26 起草。**先设计、后写代码**：本文件定下来之前不写任何代码；之后写的第一批代码也不需要真实的 R2 密钥（见“分几步做”）。云端节点（服务器整体上云）不做（决定 6）。

本文件里的价格和 R2 的行为，按 2026 年 Cloudflare 公布的资料；动手前要再核对一遍。标了“**待在真实 R2 上确认**”的，只能等主人开好账号、给服务器配好密钥后才能验证。

## 1. 目标

- 家里的 NAS 仍是唯一的原件；另在 Cloudflare R2 上存一份**私有**副本（音乐文件和封面）。
- 在家庭网络之外播放时，客户端改从 R2 取文件：不占家里有限的上行带宽，也更快。
- **家里的服务器永远照常能用**：R2 只是加速。R2 不可用、文件还没传上去、需要转码的歌，都由家里像现在一样直接发送。
- R2 只存文件，不跑任何程序：登录、权限、转码、缩放全在家里。

## 2. 传什么

| 内容 | 默认 | 理由 |
|---|---|---|
| 客户端能直接播放的原始音乐文件（flac、mp3、wav、m4a、ogg、opus 等） | 传 | 串流占用上行带宽的大头 |
| DSF、APE、WavPack 等 Windows/Android 总要转码的格式 | **不传**（主人可改） | 这些歌客户端拿到的是家里现转的 MP3，R2 上的原件用不到；只有把 R2 也当备份时才需要（见第 7 节） |
| 转码后的文件 | 不传 | 按需生成，只能在家里做 |
| 封面原图 | 传 | 很小，浏览时请求很多 |
| 缩放后的封面 | 只传客户端实际用的尺寸（600、512 等），第一次生成时顺手上传 | R2 上不能缩放 |
| Navidrome 的数据库（用户、收藏、歌单、播放记录） | **不传**（主人可改，见第 7 节） | 里面有用户数据；它不是串流需要的 |

正式曲库（2026-11-26 只读统计）：

| | 数量 | 大小 |
|---|---|---|
| 全部歌曲 | 2379 首 | 约 91.3 GB（最大一个文件 529 MB） |
| 其中 DSF + APE（默认不传） | 73 首 | 约 16.3 GB |
| 默认要传的歌曲 | 2306 首 | 约 75 GB |
| 封面原图 | 1206 张 | 约 0.14 GB |

## 3. 对象名和账本

- **对象名不透露内容**（不用歌名、路径、用户名）：
  - 音乐：`m/<歌曲 id>/<版本>`。版本是 `sha256(文件大小 | 文件修改时间)` 的前 16 位十六进制。**用文件本身的大小和修改时间，而不是数据库里的更新时间**：Navidrome 全量重新扫描时可能改写所有歌曲的更新时间，那样会把整个曲库重传一遍；文件没动，大小和修改时间就不变。
  - 封面原图：`a/<Navidrome 的图片哈希>`（由图片内容决定）。
  - 缩放封面：`r/<sha256(表示标签)>`（和本地缩放缓存同样的键）。
- **账本**：服务器自己的一张表 `sonus_r2_object`（不动 Navidrome 的表）：对象名、种类、对应的歌曲或图片、版本、大小、状态（待传 / 已传 / 待删）、上传时间、失败次数。**只有账本里“已传”、且版本和文件当前的大小与修改时间相符的，才会让客户端去 R2 取**。

## 4. 怎么和曲库保持同步

一个后台任务（在服务器进程里，不另跑程序），启动后和之后每 15 分钟做一次“对账”：

| 曲库里发生的事 | 镜像怎么做 |
|---|---|
| **新歌**（数据库里新出现、文件在） | 放进待传；传完前一直由家里直接发送 |
| **文件改了**（大小或修改时间变了，比如重新编码、改了标签写回文件） | 新版本放进待传；旧版本在新版本传完后标成待删；中间这段时间由家里直接发送（账本里的版本对不上，不会跳转） |
| **文件移动或改名** | Navidrome 的歌曲 id 由路径算出，移动后是新 id：当成“删除旧的、上传新的”，会重传这些文件 |
| **删除**（扫描器把歌曲标成丢失，或行被删） | 标成待删，**宽限 7 天**后才真正从 R2 删除（防止 NAS 暂时没挂上时误删）；7 天内文件回来就取消删除 |
| **封面变了** | 新哈希就是新对象，上传；不再被引用的旧对象宽限 7 天后删除 |
| **R2 上的对象被人手动删了，或账本丢了** | 每天一次完整核对：列出 R2 上所有对象和账本比较，缺的重新标成待传，多出来的（不在账本里）标成待删 |

上传本身：
- 一次只传一个文件，**限速**（默认例如 2 MB/s，主人定），可以只在夜里传。
- 大于 100 MB 的文件用分片上传（每片 16 MB），中断后从头续传该文件；R2 上设一条生命周期规则，自动清掉 1 天内没完成的分片（否则一直计费）。
- 上传后核对大小；失败退避重试，连续失败 5 次的不再自动重试，只在日志里报一次，等下一次每日核对。
- **每天上传字节数有上限**（默认 20 GB）：到了就暂停到第二天并在日志里报警。这是防止任何错误导致反复重传的保险。
- 第一次全量上传约 75 GB：按 2 MB/s 约 10.5 小时，按 1 MB/s 约 21 小时（可以分几个晚上传完）。

## 5. 客户端怎么从 R2 取

1. 客户端照旧请求家里的 `stream?id=…` 或 `getCoverArt?id=…`，照旧登录。
2. 家里的服务器照旧核对登录、核对这个用户能不能看到这首歌或这张图、决定要不要转码。
3. **同时满足以下几条时**，回 `302 Found`，`Location` 是一个**短时有效的 R2 签名地址**；否则一切照旧，由家里直接发送：
   - 原始文件（不转码），或者封面；
   - 账本里这个对象“已传”且版本对得上；
   - 最近一次 R2 健康检查通过；
   - 客户端在请求里声明它能处理跳转（`sonusMirror=1`；只有新版 Sonus 客户端会带，老客户端和第三方客户端完全不受影响）；
   - 客户端不在家庭网络里（客户端地址不在主人配置的家庭网段内）；主人也可以选“所有地方都用”或“完全不用”。

签名地址：
- S3 的 SigV4 查询签名（R2 兼容 S3），只允许 `GET`/`HEAD` 这一个对象；地址里没有用户名、密码。
- **有效期**默认 1 小时（够一首歌播完、来回拖动；拖动用 HTTP Range）。签名时间按整点对齐，同一小时内同一对象的地址相同，这样图片缓存能命中；代价是一个地址最多可用 2 小时。
- 地址是“持有即可访问”的：在有效期内，拿到地址的人能下载这一个文件。**只发给已登录且有权访问这首歌或这张图的用户**，日志里绝不写签名。
- 上传时给对象设好 `Content-Type`（Navidrome 的类型表）和长期缓存头（版本变了对象名就变）。

客户端对跳转的处理（代码里查到的，**待实测**）：Android 用 OkHttp，默认跟随跳转（包括 http 到 https）；Windows 把地址交给 Media Foundation，一般会跟随；网页版用 `<audio>`、`<img>`，浏览器会跟随，不需要设置 R2 的跨域。

## 6. 费用（正式曲库的规模，按 2026 年公布价格）

R2 的价格：存储每月每 GB 0.015 美元（前 10 GB 免费）；A 类操作（写入、列举、开始/完成分片上传）每月前 100 万次免费，之后每百万次 4.5 美元；B 类操作（读取、HEAD）每月前 1000 万次免费，之后每百万次 0.36 美元；**流出流量免费**。

| 项目 | 次数或大小 | 费用 |
|---|---|---|
| 存储（默认，约 75 GB） | 约 65 GB 计费 | 每月约 **1.0 美元** |
| 存储（全部传，约 91 GB，当备份用时） | 约 81 GB 计费 | 每月约 1.2 美元 |
| 第一次上传（A 类） | 约 2300 个文件：普通上传和分片上传合计约 1 万次请求；封面原图和常用缩放图约 3000 次 | 一次性，免费额度内 |
| 日常同步（A 类） | 每天核对列举约 5 次（每次最多 1000 个对象），新歌上传几十次 | 每月几百次，免费额度内 |
| 健康检查（B 类） | 每分钟 1 次 HEAD，每月约 4.3 万次 | 免费额度内 |
| 播放和浏览（B 类） | 假设在外每天播 100 首（每首约 3 次读取：开始和拖动）、看 500 张封面：每月约 2.4 万次 | 免费额度内 |
| 流量 | 不论多少 | 免费 |

**合计：每月约 1 美元**（存储），读写次数都远低于免费额度。

可能让费用失控的情况：
- 反复重传（版本算错）：版本只取文件大小和修改时间，加上每天 20 GB 的上传上限。
- 未完成的分片上传一直计费：用生命周期规则自动清理。
- 签名地址被转发、反复下载：读取很便宜、流量免费；地址会过期、只发给有权限的用户。
- 建议主人在 Cloudflare 设一个**费用提醒**（例如每月超过 5 美元），这只有主人能设。

## 7. 恢复

“恢复”有两种情况：

**A. R2 上的副本丢了或坏了**（存储桶被删、对象被删、换了账号）：把账本清空，后台任务会把所有文件重新传一遍，时间和第一次上传一样（75 GB 约 10 到 21 小时）。这期间客户端照常由家里直接发送，不影响使用。

**B. 用 R2 恢复家里的音乐**（NAS 的硬盘坏了）：只有主人决定把 R2 也当作**备份**时才可能，而且需要额外做几件事：
- **所有格式都要传**（包括 DSF、APE），否则这些文件恢复不了；
- **每天把“对象名 → 媒体库里的相对路径”的清单传到 R2**（`manifest/<日期>.json.gz`）。因为对象名是不透明的，没有清单就不知道每个文件原来叫什么、在哪个文件夹。清单里有歌曲的路径（通常含歌名、艺人名），放在私有存储桶里；
- 一个恢复命令（例如 `sonus-server r2-restore --to <文件夹>`），按最新清单把文件下载回原来的路径，核对大小，可以中断后接着下；
- **数据库**（用户、收藏、歌单、播放记录）要不要也备份到 R2：如果要，备份前用主人的 `PasswordEncryptionKey` 之外再单独加密，每天一份，保留 14 份。

**这不是完整的备份方案**：
- R2 目前没有对象的历史版本（**待在真实 R2 上确认**）。家里误删的文件，7 天宽限期后 R2 上也会删掉。
- 家里的文件被损坏（比如被勒索软件加密）时，修改时间变了，就会被当作“文件改了”，把损坏的版本传上去，再删掉旧的。
- 真正的备份仍建议另做；这里能做的，是让“镜像”在硬盘坏了时多一条路。

## 8. 密钥和存储桶设置（主人提供）

主人需要提供（**只放在服务器的运行环境里，不发给任何会话，不放进代码仓库、镜像、PR 或聊天**）：

| 项目 | 放在哪里 |
|---|---|
| Cloudflare 账户 ID（用来拼接口地址 `https://<账户 ID>.r2.cloudflarestorage.com`） | Unraid 上服务器容器的环境变量 `SONUS_R2_ACCOUNT_ID` |
| 存储桶名 | 环境变量 `SONUS_R2_BUCKET` |
| **只对这一个存储桶有“对象读写”权限的 API 令牌**：Access Key ID 和 Secret Access Key（不要用账户级的全局密钥） | 环境变量 `SONUS_R2_ACCESS_KEY_ID`、`SONUS_R2_SECRET_ACCESS_KEY`；或者 `/data` 下一个只有服务器能读的文件（权限 0600） |

存储桶的设置：
- **私有**：不开 r2.dev 公共地址，不绑定公开的自定义域名（所有访问都靠签名地址）。
- 生命周期规则：1 天内没完成的分片上传自动清理。
- 位置提示：选离主人常去的国外地区近的，或者“自动”。
- 不需要跨域（CORS）设置（除非以后网页版改用 `fetch` 取文件）。

服务器程序里：密钥只在内存中；调试输出一律显示“已设置”；日志绝不写密钥、签名或带签名的地址。

## 9. 出问题时会怎样

| 情况 | 服务器怎么做 | 用户感觉到什么 |
|---|---|---|
| R2 连不上 | 每分钟的健康检查失败，立刻停止所有跳转，直到恢复；上传暂停、稍后重试 | 最多一次失败后自动改由家里发送（新版客户端会重试） |
| 密钥错了、被撤销、过期 | 健康检查和上传返回 401/403：停止跳转和上传，日志报一次 | 同上；镜像不再更新，直到主人换好密钥 |
| 存储桶被删 | 同上；每日核对发现后，账本里全部标成待传 | 同上 |
| 账户欠费或被停用 | 同上 | 同上 |
| 服务器时钟不准（签名要求时间误差在 15 分钟内） | R2 拒绝签名：健康检查失败，停止跳转 | 由家里直接发送 |
| 文件还没传上去 / 正在传 / 版本对不上 | 不跳转 | 由家里直接发送，和现在一样 |
| 上传中途断了，或上传时文件正在被改写 | 大小对不上：不标“已传”，稍后整个文件重传 | 无 |
| 有人拿到了签名地址 | 有效期内能下载那一个文件；过期后失效 | 无；对象名不透露歌名 |
| 客户端不会跟随跳转 | 只对声明 `sonusMirror=1` 的客户端跳转 | 无 |
| 家庭网段配错 | 在家的客户端也会去 R2 取（慢一点，但能用），或在外的仍由家里发送 | 速度不同，功能正常 |
| 每天上传量到了上限 | 暂停上传到第二天，日志报警 | 新歌晚一天上 R2 |
| 家里的服务器本身停了 | 拿不到签名地址（登录和权限都在家里） | 和现在一样：服务器停了就用不了 |

## 10. 不用真实 R2 能在本机测试什么

- **签名算法**：用 AWS 文档里公布的 SigV4 标准示例（固定的密钥、时间和请求，已知正确的签名）做单元测试，不靠我们自己的实现“自证”。
- **上传、同步、恢复、跳转、各种出错**：测试里起一个**自己写的假 S3 服务**（只在 127.0.0.1，数据在内存里，接受上传、分片上传、下载、HEAD、列举和删除，并按同样的规则核对签名和有效期，能模拟断网、403、超时、对象丢失）。这样能测：
  - 账本和对账（新增、修改、移动、删除和宽限期、手动删对象）；
  - 限速和每日上限；
  - 分片续传；
  - 健康检查；
  - 跳转的每个条件，以及每种“不跳转”的情况；
  - 恢复命令；
  - 日志里不出现密钥和签名。
- **MinIO**（真正兼容 S3 的开源服务）可以再做一次额外的核对，确认我们的签名和请求是真 S3 服务也接受的。它需要**另外下载**（约 100 MB 的单个程序，只放在测试临时目录、不安装到系统），**要先问主人**。不用它也能把代码写完、测完。
- **只能在真实 R2 上确认的**：
  - 真实的签名地址能否用；
  - R2 对 `Range`、条件请求、`Content-Type` 的处理；
  - 分片上传的限制；
  - 有没有对象历史版本；
  - 三个客户端在真实网络下跟随跳转、拖动、出错后改由家里发送；
  - 上传对家里网络的实际影响；
  - 一个月后的实际账单。

## 11. 分几步做

1. **R2-a**（不需要主人的密钥）：
   - SigV4 签名（含标准示例）、HTTPS 客户端（新依赖 `rustls`/`hyper-rustls`；SigV4 自己写，不引入庞大的 AWS SDK）；
   - 配置项，**默认关闭**：没填密钥时整个功能不启动，行为和现在完全一样；
   - 账本、对账和上传任务、健康检查、假 S3 测试。
2. **R2-b**（不需要主人的密钥）：`stream`、`getCoverArt` 的跳转（只对 `sonusMirror=1`）、家庭网段判断。如果主人要备份：清单和恢复命令。
3. **客户端**（由负责客户端的会话做）：Windows、Android、网页版带上 `sonusMirror=1`，跟随跳转，失败时用 `sonusMirror=0` 重新请求。
4. **上线**（需要主人）：开通 R2、建存储桶和令牌、填进 Unraid 的环境变量、设费用提醒；先只开上传，观察几天的速度和账单，再开跳转。
