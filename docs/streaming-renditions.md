# 播放库设计：统一的播放格式、自带解码、音质设置

2026-11-28 起草，同日按主人的意见改为第二版（音质设置可以强制无损、客户端自带解码、新的播放库），主人逐项定下了第 11 节。**先设计、后写代码**；第一步是原型和静默实测（第 9 节）。

本文件里的曲库数字是 2026-11-28 对正式服务器的只读统计；凡是标了“**待实测**”的，都要等第 0 步做完才算数。

## 1. 为什么要做

现在服务器把原始文件直接发给客户端，每个客户端用自己平台的解码器去解：Windows 用系统自带的 Media Foundation，安卓用 ExoPlayer，网页用浏览器。原始文件五花八门（MP3、FLAC、WAV、DSF、APE，采样率从 44.1 kHz 到 192 kHz，还有 DSD）。已经遇到过的问题：

- **从中间接手 FLAC 会跳到下一首**（Windows 0.7.0）：Media Foundation 开始解码后再跳位置，会解码失败。旧播放核心已修正（先打开、跳到位置、再播放），没有单独发版，随 0.8.0 发布；FLAC 刚开始播放的一瞬间就跳进度仍会这样，新核心解决。
- **Windows 读 FLAC 总是从头下载**：文件有寻址表也一样。所以从中间接手一首歌要等下载到那个位置（实测 2–6 秒），跳进度也一样。
- **有的文件在 Windows 上解码失败**（例如 11-27 的「不该」）。
- **DSF、APE 只能实时转成 MP3**：这 73 首在 Windows 和安卓上听到的其实是有损的 MP3。
- **在外面用手机流量**：高解析度 FLAC 码率很高（96 kHz/24 位约 3 Mbps），费流量、容易卡。
- **没有音量均衡**：不同专辑响度差很多。

## 2. Spotify 怎么做（公开资料）

- 每首歌入库时就转成少数几种固定格式和码率（桌面和手机主要用 Ogg Vorbis，网页用 AAC，2025 年起有 FLAC 无损），客户端从不直接拿原始母带。
- 播放器用自己带的解码器，不依赖操作系统，各平台行为一致；文件带索引、按字节范围取，跳进度和切换设备基本不用等。
- 音质按网络分开设：Wi-Fi、移动网络、下载各有一档（低 / 普通 / 高 / 极高 / 无损），可以选“自动”。
- 有音量均衡（安静 / 正常 / 大声），靠入库时测好的响度。

我们借用这几条：**服务器准备好规整的文件，客户端只面对两种格式，自己解码，音质和音量由用户设置。**

## 3. 目标

1. **播放格式只有两种**：无损用 FLAC，有损用 Opus。文件规整、带完整寻址表，三端都能按字节范围跳。
2. **切换设备即播、跳进度不等**。
3. **音质由用户定**，可以强制无损；无损就是真无损（和原文件逐个采样相同，DSD 除外，见第 4 节）。
4. **DSF、APE 也是无损**，不再是 MP3。
5. **音量均衡**（默认关，可以打开）。
6. **原文件一个字节都不动，文件夹也不整理**；播放库随时可以删掉重建；老客户端、第三方客户端完全不受影响。

## 4. 播放库：原文件是母带，播放版从它生成

**原文件和文件夹保持原样。** Navidrome 按文件路径给每首歌编号，收藏、歌单、播放次数、正在播放的会话、R2 镜像的账本都挂在这个编号上；挪动或改名会让这些全部断掉。所以不整理原文件，另建一个**播放库**：

- 服务器自己的一张表（放在服务器自己的数据库文件里，和 R2 账本一样，不动 Navidrome 的数据库），每首歌每一档一行：
  `歌曲 id · 原文件版本（大小 + 修改时间） · 档位 · 格式 · 采样率 · 位深 · 声道 · 采样总数 · 文件大小 · 响度（LUFS）· 峰值 · 状态 · 校验结果 · 生成时间`
- 文件放在 NAS 应用数据盘上自己的文件夹（例如 `appdata/sonus/library`），文件名用“歌曲 id + 原文件版本 + 档位”，不含歌名和路径。
- 整个播放库是派生出来的：表和文件夹删掉，服务器会重新生成，期间照旧发原文件。

**档位**

| 档位 | 格式 | 从哪些原文件生成 | 说明 |
|---|---|---|---|
| **无损** | FLAC，每秒一个寻址点 | FLAC、WAV、APE、DSF | 保留原采样率和位深（主人定）；FLAC/WAV/APE 解出来的采样和原文件逐个相同。DSF（DSD）先转成 24 位 PCM（88.2 kHz，DSD 常用的换算），这是唯一会改变数据的地方 |
| **极高** | Opus 256 kbps | 无损原文件 | 听感接近无损 |
| **高** | Opus 160 kbps | 无损原文件；MP3 原文件 | 移动网络的默认 |
| **普通** | Opus 96 kbps | 无损原文件；MP3 原文件 | 省流量 |

- **MP3 原文件**（1154 首，平均 287 kbps）：选“无损”或“极高”时直接发原文件（再转只会更差）；选“高”“普通”时发转好的 Opus。
- **体检**：每份播放版生成后从头解码到尾，并核对时长（和原文件相差不超过 0.1 秒）。原文件解不了、时长不对的，列进一份“曲库体检”清单（设置页和日志里能看到），原文件怎么处理由主人决定，服务器不改它。
- **响度**：生成时用 EBU R128 测好每首歌和每张专辑的响度，存进表里，客户端做音量均衡时用。

## 5. 音质设置（三端一致）

| 设置 | 选项 | 默认 |
|---|---|---|
| **Wi-Fi 下的音质** | 自动 / 普通 / 高 / 极高 / 无损 | 自动（= 无损） |
| **移动网络下的音质** | 自动 / 普通 / 高 / 极高 / 无损 | 自动（= 高） |
| **音量均衡** | 关 / 安静 / 正常 / 大声；按歌曲 / 按专辑 | 关（打开时：正常、按专辑） |
| **始终用原文件**（高级） | 开 / 关 | 关；开了就照现在的方式发原文件，音质设置不起作用 |

- **强制无损**：两项都选“无损”。
- 播放栏上显示当前这首实际用的是哪一档（例如“无损 · 96 kHz/24 位”或“Opus 160”）。
- 电脑一般按 Wi-Fi 处理；手机按系统报告的网络类型切换，换网络时下一首起生效。
- 网速跟不上时（缓冲超过几秒）：只在选了“自动”时临时降一档，强制的档位不降（Spotify 也是这样）。
- 以后做离线下载时，再加一项“下载音质”。

## 6. 客户端自带解码

| 客户端 | 现在 | 改成 |
|---|---|---|
| **Windows** | Media Foundation（系统的） | **自带**：FLAC 和 Opus 解码器（都是许可宽松的开源库，或它们的纯 C# 版本，第 0 步定），自己按字节范围下载、按寻址表跳；WASAPI 输出声音；系统媒体控件（键盘媒体键、锁屏卡片）另外接 |
| **安卓** | ExoPlayer | **保留**：它本来就是自带的那一类（自己读文件、自己按范围取），FLAC 和 Opus 在 Android 13 以上都有解码器；只把格式固定下来 |
| **网页** | 浏览器 | 浏览器原生支持 FLAC 和 Opus（Chrome、Edge、Firefox、新版 Safari），**待实测** |

Windows 自带解码以后：
- 切换设备即播：要第 63 秒，就按寻址表直接取那一段。
- 无缝衔接按采样精确拼接（Opus 文件里记着开头要去掉多少采样）。
- 解码失败时知道失败在哪一帧，能跳过坏帧继续，而不是整首放弃。
- 以后可以加“独占模式”（声音不经 Windows 混音，按原采样率送给声卡），给高解析度用。
- 代价：Windows 播放核心重写（L 级），要保留现在的所有行为（无缝衔接、ReplayGain、输出设备选择、系统媒体控件、Connect 的上报），所以分开做、单独验收。

## 7. 服务器怎么生成、怎么发送

**生成**
- 服务器进程里的后台任务，用容器里已有的 ffmpeg（6.1）；参数固定，不接受客户端提供的任何路径或参数，受并发和输出大小上限约束（和现在的转码一样）。
- 并行任务默认 8 个、低优先级（服务器 32 核），可以只在夜里跑；正常播放和实时转码优先。
- 新歌入库、文件改了（大小或修改时间变了）自动重新生成；歌删了，播放版宽限 7 天后删。对账和 R2 镜像是同一套思路（`docs/r2-mirror.md` 第 4 节），共用代码。

**发送**
- 新版 Sonus 客户端在 `stream` 请求里说要哪一档（例如 `sonusQuality=lossless`、`veryHigh`、`high`、`normal`）。服务器核对登录和权限后，有这一档就发（支持按范围取）；还没生成好，就照现在的方式发原文件或实时转码，客户端不用关心。回复里带上实际是哪一档、什么格式、多少采样率，客户端显示在播放栏上。
- 不带这个参数的请求（老客户端、第三方客户端）完全照旧。
- 新增一个只读接口给客户端查“这首歌有哪些档位、响度多少”（音量均衡和播放栏显示用），具体形式在第 1 步定。

**和 R2 镜像的关系**：R2 上照旧存原文件当备份（R2 设计不变）；另外存“高”档（Opus 160），在外面时跳转到它。

## 10. 风险

- **Windows 播放核心重写**是这几步里最大的一块。缓解：第 0 步先做原型，确认解码、按范围跳、出声都可行再动手；新旧核心可以并存一段时间（设置里切换），出问题能马上换回。
- **网页对 FLAC/Opus 的支持**以实测为准；不行的浏览器退回现在的方式。
- **DSD 转 PCM**会改变数据（这是 DSD 的本质，Spotify 也不提供 DSD）；第 0 步做频谱检查。
- **生成任务占用 NAS**：限并发、低优先级、可以只在夜里跑。

## 12. 第 0 步实测结果（2026-11-28）

以下实测全部在本机（Windows 11 ARM64）后台静默完成，未连接正式服务器、未弹出窗口、未发出声音。下载的三个 NuGet 包及 APE 样本处理方式均已由主人提前确认。

### 12.1 样本与 ffmpeg 生成实测

测试样本均在本地临时目录生成（不进仓库）：
- **真实 libFLAC 1.5.0 FLAC**（Windows `MediaTranscoder` / `mkflac`）：44.1 kHz/16 位（两首各 180 秒，22.2 MB）、96 kHz/24 位（180 秒，82.5 MB）、192 kHz/24 位（180 秒，164.0 MB）。
- **WAV**：44.1 kHz/16 位（180 秒，31.8 MB）、96 kHz/24 位（180 秒，103.7 MB）。
- **MP3**：320 kbps CBR（180 秒，7.2 MB）。
- **DSF（DSD64）**：本地脚本按 Sony DSF 规范生成的 2.8224 MHz 1 位立体声 ΔΣ 调制信号（30 秒，21.2 MB，含 1/5/15 kHz 与 1.5/7/18 kHz 乐音及 20 kHz 以上整形噪声）。
- **APE**：本机 ffmpeg 仅支持解码 APE、不能编码 APE；经主人同意第 0 步跳过自制 APE 样本，ffmpeg 内置 `ape` 解码器输出整数 PCM，走与 FLAC/WAV 相同的无损 `-c:a flac` 管线，留待 NAS 试运行时覆盖真实 APE。

使用本机 BtbN ffmpeg 7.1.5 ARM64（全部参数仅用 ffmpeg 6.1 与 7.1 通用的标准选项，不依赖 `libsoxr`）生成各档位及响度测量的单线程实测：

| 源文件（时长 / 体积） | 无损 FLAC | 极高 Opus 256 | 高 Opus 160 | 普通 Opus 96 | EBU R128 响度 |
|---|---|---|---|---|---|
| FLAC 44.1/16（180 s / 22.2 MB） | 22.6 MB · 345 ms（522x）· 逐采样一致 | 6.0 MB · 1.29 s（139x） | 3.9 MB · 1.25 s（145x） | 2.5 MB · 1.17 s（154x） | 1.19 s（151x）· −10.8 LUFS |
| FLAC 96/24（180 s / 82.5 MB） | 82.5 MB · 672 ms（268x）· 逐采样一致 | 6.1 MB · 1.34 s（134x） | 4.0 MB · 1.22 s（148x） | 2.7 MB · 1.37 s（131x） | 1.42 s（127x）· −10.6 LUFS |
| FLAC 192/24（180 s / 164.0 MB） | 163.8 MB · 1.36 s（132x）· 逐采样一致 | 6.1 MB · 1.53 s（118x） | 4.1 MB · 1.43 s（126x） | 2.7 MB · 1.12 s（161x） | 1.15 s（157x）· −10.4 LUFS |
| WAV 44.1/16（180 s / 31.8 MB） | 22.6 MB · 356 ms（506x）· 逐采样一致 | 6.0 MB · 1.32 s（137x） | 3.9 MB · 1.42 s（127x） | 2.5 MB · 1.25 s（144x） | 1.32 s（137x）· −10.8 LUFS |

| DSF DSD64（30 s / 21.2 MB） | 12.1 MB（88.2/24）· 298 ms（101x） | 1.4 MB · 234 ms（128x） | 1.1 MB · 232 ms（130x） | 0.75 MB · 229 ms（131x） | 389 ms（77x）· −9.6 LUFS |

**两项重要发现**：
1. **ffmpeg 的 FLAC 编码器/封装器不写 `SEEKTABLE`**（仅写入 `STREAMINFO`、`VORBIS_COMMENT`、`PADDING`）。因此在第 1 步由 Rust 服务器在 ffmpeg 写完临时文件后直接扫描帧头并插入每秒一个寻址点的 `SEEKTABLE`（同时回填 `STREAMINFO` 的最小/最大帧长），实测单文件耗时 22–425 ms，无需在镜像里额外安装 `metaflac`/`flac` 工具，且在 ffmpeg 6.1 与 7.1 上完全一致。
2. **首次全量生成时间估算修正**：按实测速度推算，正式曲库（2379 首、166.8 小时）含四档转码、EBU R128 测量与全曲体检解码，在 8 并行任务下预计约 **35–50 分钟**完成（快于第 8 节原估的 2 小时）。
3. **体检解码耗时**：180 秒单曲从头解码核对耗时 107–592 ms，FLAC 时长偏差 `0.0000 s`，Opus 时长偏差 `0.0065 s`（标准的 312 采样 `pre_skip` 封装差，远小于 0.1 s 阈值）。

### 12.2 DSD 转 PCM（88.2 kHz / 24 位）低通滤波与频谱检查

对 2.8224 MHz DSD64 样本（左声道 1 / 5 / 15 kHz，右声道 1.5 / 7 / 18 kHz）对比了五组 ffmpeg 内置 `swr`/`lavfi` 滤波参数，并在 88.2 kHz 输出上做 65536 点 Hann 窗 FFT 频谱分析：

| 方案（ffmpeg 滤镜参数） | 1 kHz | 5 kHz | 15 kHz | 18 kHz | 20–24 kHz 噪声均值 | 24–30 kHz 噪声均值 | 30–44 kHz 噪声均值 |
|---|---|---|---|---|---|---|---|
| 默认重采样（`-ar 88200`） | −15.2 dB | −21.7 dB | −28.5 dB | −28.1 dB | −91.1 dB | −89.3 dB | −92.4 dB |
| 二阶 IIR（`lowpass=f=30000:poles=2,aresample=88200`） | −15.2 dB | −21.7 dB | −28.7 dB | −28.6 dB | −92.3 dB | −91.6 dB | −97.0 dB |
| 四阶 IIR（2×`lowpass=f=24000:poles=2,aresample=88200`） | −15.2 dB | −21.7 dB | −29.7 dB | −30.5 dB | −96.0 dB | −97.8 dB | −106.9 dB |
| **线性相位 FIR 0.60（`aresample=88200:filter_size=128:cutoff=0.60`）** | **−15.2 dB** | **−21.7 dB** | **−28.5 dB** | **−28.1 dB** | **−91.1 dB** | **−95.4 dB** | **−180.0 dB** |
| 线性相位 FIR 0.55（`aresample=88200:filter_size=128:cutoff=0.55`） | −15.2 dB | −21.7 dB | −28.5 dB | −28.1 dB | −91.2 dB | −108.6 dB | −180.0 dB |

**结论**：采用 **`aresample=88200:filter_size=128:cutoff=0.60`**（线性相位加窗 sinc FIR，截止点约 26.5 kHz），配合 `-sample_fmt s32 -bits_per_raw_sample 24` 编成 24 位 FLAC。它在 0–20 kHz 可听频段内衰减为 **0.0 dB** 且无相位失真，同时将 30 kHz 以上 DSD 超声量化噪声彻底压至 **−180 dB**；并且属于 ffmpeg 标准内置滤镜（6.1 / 7.1 通用）。DSF 的 Opus 档位从已过滤好的无损 FLAC 生成，避免超声噪声干扰 Opus 码率分配。

### 12.3 Windows 自带解码原型与 Media Foundation 对比实测

独立原型（位于临时目录，未改动 `src/Sonus`）采用 **纯 C#（AnyCPU，零原生 DLL）** 方案：
- **FLAC 解码 / Ogg 分页与二分寻址 / WAV 解码 / HTTP Range 分块缓存**：自写纯 C#（RFC 9639 / RFC 7845，零外部依赖）。
- **Opus 解码**：`Concentus` 2.2.3（BSD-3-Clause，约 854 KB，零传递依赖）。
- **WASAPI 输出与纯 C# 重采样**：`NAudio.Wasapi` 3.3.0 + `NAudio.Core` 3.3.0（MIT，约 287 KB）。
- **MP3 解码**（供 MP3 原文件与“始终用原文件”使用）：`NLayer` 3.0.1（MIT，约 60 KB）。

**解码正确性与纯解码吞吐（单核）**：

### 12.4 安卓（ExoPlayer）与网页（Edge / Chromium）实测

- **安卓（`sonus-phone` 模拟器，Android API 37，Media3 ExoPlayer，静音）**：8 个测试文件全部通过（FLAC 44.1/16、96/24、192/24、88.2/24 DSD 转换版、Opus 256/160/96、MP3 320）。
  - FLAC 96/24 与 192/24 均保持原生采样率与 24 位 PCM 输出（`pcmEncoding=21`），首播 154–279 ms，跳到第 60 秒 **129–256 ms**（仅 2 次 HTTP Range 请求）。
  - Opus 256/160/96 首播 188–300 ms，跳到第 60 秒 **78–146 ms**。
- **网页（Microsoft Edge 无头静音，Chromium 内核）**：8 个测试文件全部解码并正常跳转（包括 **192 kHz/24 位 FLAC**：首播 14 ms、跳第 60 秒 24 ms；Opus 256/160/96：首播 12–15 ms、跳第 60 秒 29–34 ms）。
  - **关键兼容发现**：浏览器对 `canPlayType('audio/opus')` 返回空字符串（不支持），而对 `canPlayType('audio/ogg; codecs=opus')` 返回 `"probably"`；因此服务器发送 Opus 播放版时必须返回 `Content-Type: audio/ogg`（或 `audio/ogg; codecs=opus`），网页端检测格式能力时也必须用 `audio/ogg; codecs=opus`。

### 12.5 根据实测敲定的第 1–3 步实现细节

1. **Windows 播放核心选型**：**确定使用纯 C# 方案**（自写 FLAC/Ogg/WAV + `Concentus` 2.2.3 + `NAudio.Wasapi` 3.3.0 + `NLayer` 3.0.1），无需编译和打包任何 ARM64/x64 原生 DLL，两套架构行为完全一致，CPU 与内存开销极低。
2. **服务器 FLAC 寻址表与 Opus MIME**：服务器生成无损 FLAC 后由 Rust 插入精确的 1 秒 `SEEKTABLE` 并回填帧大小；Opus 档位以 Ogg 容器封装并返回 `Content-Type: audio/ogg`；DSD 转 PCM 固定使用 `aresample=88200:filter_size=128:cutoff=0.60`。
3. **HTTP Range 块大小优化**：原型使用 128 KB 块；第 2 步对有损格式二分寻址可采用 64 KB 块以进一步减少外网跳转流量。
