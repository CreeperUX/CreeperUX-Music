# 播放版设计：服务器为每首歌准备规整的播放文件

2026-11-28 起草，**待主人定**（第 9 节）。**先设计、后写代码**；第一步是用静默测试实测候选格式，再定格式（第 7 节）。

本文件里的曲库数字是 2026-11-28 对正式服务器的只读统计；格式在各平台上的表现，凡是标了“**待实测**”的，都要等第 0 步测完才算数。

## 1. 为什么要做

现在服务器把原始文件直接发给客户端，每个客户端用自己平台的解码器去解：Windows 用系统自带的 Media Foundation，安卓用 ExoPlayer，网页用浏览器。三套解码器各有各的毛病，而原始文件五花八门（MP3、FLAC、WAV、DSF、APE，采样率从 44.1 kHz 到 192 kHz，还有 DSD）。已经遇到过的问题：

- **从中间接手 FLAC 会跳到下一首**（Windows 0.7.0，0.7.1 修正）：Media Foundation 在开始解码后再跳位置，会解码失败。
- **Windows 读 FLAC 总是从头下载**：就算文件有寻址表也一样。所以从中间接手一首歌，要等文件下载到那个位置才能出声，接手越靠后等得越久（实测 2–6 秒）。跳进度也一样。
- **有的文件在 Windows 上解码失败**（例如 11-27 的「不该」）。
- **DSF、APE 只能实时转成 MP3**：这 73 首在 Windows 和安卓上听到的其实是有损的 MP3。
- **在外面用手机流量时**，高解析度 FLAC 码率很高（96 kHz/24 位约 3 Mbps），费流量、容易卡。

## 2. Spotify 怎么做（公开资料）

- 每首歌入库时就转成少数几种固定格式和码率（桌面和手机主要用 Ogg Vorbis，网页用 AAC，2025 年起有 FLAC 无损），客户端从不直接拿原始母带。
- 播放器用自己带的解码器，不依赖操作系统，所以各平台行为一致。
- 文件带索引、按字节范围请求，跳进度和切换设备时直接取那一段，基本不用等。
- 客户端会预取下一首、缓存常听的歌。

我们不需要照搬（我们只有一个用户、一台 NAS），但“**服务器提前准备好规整的文件，客户端只面对少数几种格式**”这一条可以直接借用。

## 3. 目标

1. 客户端拿到的永远是**规整的文件**：格式只有两三种，带完整的索引，三端都能按字节范围跳进度。
2. **切换设备即播**：从中间接手一首歌，不用等下载到那个位置。
3. **音质不降**：在家里听的仍然是无损；DSF、APE 也变成无损，不再是 MP3。
4. **在外面省流量**：自动用高品质的有损版。
5. **原文件一个字节都不动**；播放版随时可以删掉重做；老客户端、第三方客户端完全不受影响。

## 4. 播放版是什么

服务器在后台为每首歌生成最多两份“播放版”，放在 NAS 上自己的文件夹里：

| 档位 | 用在哪里 | 候选格式（第 0 步实测后定） | 来源 |
|---|---|---|---|
| **无损档** | 家里、Wi-Fi | ① FLAC，每秒一个寻址点；② ALAC（苹果无损），MP4 封装，自带样本索引 | 无损原文件（FLAC、WAV、APE、DSF） |
| **省流档** | 手机流量、外面 | ① AAC 256 kbps，MP4 封装；② Opus 192 kbps | 无损原文件 |

- **MP3 原文件不再转码**：它本身就是有损的，平均 287 kbps，再转一次只会更差。两档都直接用原文件（MP3 在三端都能按范围跳，**待实测**确认）。
- **DSF（DSD）**转成 24 位 PCM 后再编码（88.2 kHz，DSD 常用的换算），这样 DSD 也能无损地播，不再是 MP3。
- **高解析度**（96 / 176.4 / 192 kHz）：默认**保留原采样率**（主人定，第 9 节）。
- 为什么偏向 MP4 封装：MP4 文件开头就有每一小段在文件里的位置表，播放器要跳到第 63 秒，可以直接去取那一段。Windows 读 FLAC 时不这样做，而是从头下载（第 1 节）。所以无损档很可能要用 ALAC（MP4），但安卓和网页对 ALAC 的支持**待实测**。

## 5. 怎么生成、存在哪、怎么发送

**生成**
- 服务器进程里的一个后台任务（不另跑程序），用容器里已有的 ffmpeg（6.1）；参数固定，不接受客户端提供的任何路径或参数，和现在的转码一样受并发和输出大小的上限约束。
- 并行任务数默认 8，低优先级（服务器有 32 核），可以只在夜里跑。
- 新歌入库、文件改了（大小或修改时间变了），自动重新生成；歌删了，播放版宽限 7 天后删。这套对账和 R2 镜像是同一套思路（`docs/r2-mirror.md` 第 4 节），可以共用代码。
- 生成后自己核对：时长和原文件相差不超过 0.1 秒、能从头解码到尾，不通过的不用，日志里报一次。

**存储**
- 放在 NAS 的应用数据盘上自己的文件夹（例如 `appdata/sonus/renditions`），文件名用“歌曲 id + 原文件版本 + 档位”，不含歌名、路径。
- 播放版只是缓存：整个文件夹删掉，服务器会慢慢重新生成，期间照旧发原文件。

**发送**
- 新版 Sonus 客户端在 `stream` 请求里声明要哪一档（例如 `sonusRendition=lossless` 或 `compact`）。服务器核对登录和权限后：播放版已经生成好，就发播放版（支持按范围请求）；还没生成好，就照现在的方式发原文件或实时转码。客户端不需要关心。
- 不带这个参数的请求（老客户端、第三方客户端、网页的旧版本）完全照旧。
- 和 R2 镜像的关系：在外面时，客户端要省流档，服务器跳转到 R2 上的省流档副本（比原文件小得多）；R2 上照旧保留原文件当备份（R2 设计不变）。

| | 额外空间 | 首次全部生成 |

- 之后每天只处理新歌和改过的歌，几乎没有负担。

## 8. 风险

- **ALAC 在安卓和网页上可能放不了**：Chrome 不支持 ALAC。如果实测证实，无损档可以按客户端选格式（Windows 用 ALAC，安卓和网页用 FLAC），代价是多一份空间。第 0 步会给出结论。
- **无缝衔接**：AAC 编码会在开头加一小段填充，播放器要靠文件里的信息把它去掉，否则两首歌之间会有极短的空隙。第 0 步要测。
- **DSD 转 PCM 的音质**：转换方式按常用做法，第 0 步会做频谱检查。
- **生成任务占用 NAS**：限并发、低优先级、可以只在夜里跑；正常播放、转码优先。
- **新增代码量**：服务器端 M 级（生成、对账、发送），客户端 S–M 级（选档位、设置项）。

## 9. 要主人定的事

1. **无损档要不要保留原采样率？** 推荐保留（空间够；96/192 kHz 的歌照原样听）。
2. **省流档用什么码率？** 推荐 AAC 256 kbps（三端都原生支持，听感接近无损）；第 0 步也会测 Opus。
3. **什么时候用哪一档？** 推荐：家里和 Wi-Fi 用无损档；手机流量和在外面用省流档；设置里可以改。
4. **要不要保留“始终用原文件”的选项？** 推荐保留，方便对比和排查。
5. **先做第 0 步吗？** 推荐先做：一天左右、全静默、不碰线上，做完再决定后面几步。
