# R2 镜像设计（阶段 5 第 5 部分，决定 6）

2026-11-26 起草，**先设计、后写代码**。写代码前要请主人定的事列在最后（“要主人定的事”）。本文件里所有价格和 R2 的行为，都按 2026 年 Cloudflare 公布的资料，动手前要再核对一遍；标了“待在真实 R2 上确认”的，只能等有了主人的账号和密钥才能验证。

## 目标

- 家里的 NAS 仍是唯一的原件；另在 Cloudflare R2 上保存一份**私有**副本（音乐文件和封面）。
- 在国外（家庭网络之外）播放时，客户端改从 R2 取文件：不经过家里有限的上行带宽，也更快（R2 在 Cloudflare 的全球网络上）。
- **家里的服务器永远照常能用**：R2 是加速，不是依赖。R2 不可用、文件还没传上去、需要转码的歌，都由家里的服务器像现在一样直接发送。
- 不做云端节点（决定 6）：R2 只存文件，不跑任何程序；登录、权限、转码、缩放都还在家里。

## 范围：传什么

| 内容 | 传不传 | 理由 |
|---|---|---|
| 原始音乐文件（flac、mp3、wav、m4a、ogg、opus 等客户端能直接播放的） | 传 | 这就是“串流”占用上行带宽的大头 |
| DSF、APE、WavPack 等 Windows/Android 客户端总是要求转码的格式 | **默认不传** | 这些歌客户端拿到的是家里现转的 MP3，原件放在 R2 上用不到（正式曲库里这类约 16 GB，占 18%）；网页版对浏览器播放不了的格式也是要转码的 |
| 转码后的文件 | 不传 | 每个请求参数不同、按需生成；转码只能在家里做 |
| 封面原图（Navidrome 的图片仓库和文件夹里的封面） | 传 | 体积小（正式曲库约 140 MB），浏览时请求很多 |
| 缩放后的封面 | 只传客户端实际要的尺寸，在生成时顺手上传（见下） | 不能在 R2 上缩放；客户端只用 600（Windows、Android）和 512（网页）等少数尺寸 |

正式曲库（只读统计，2026-11-26）：2379 首歌共约 **91.3 GB**（最大一个文件 529 MB），去掉总要转码的 DSF/APE 后约 **75 GB**；封面原图 1206 张约 0.14 GB。

## 什么时候传、怎么记账

- **对象名不泄露内容**：不用歌名或路径，用不透明的键：
  - 音乐：`m/<歌曲 id>/<版本>`，版本是 `sha256(歌曲的 updated_at | size)` 的前 16 位十六进制；文件变了（重新扫描后 `updated_at`、`size` 变）就是新对象。
  - 封面原图：`a/<Navidrome 的图片哈希>`（本来就由图片内容决定）。
  - 缩放封面：`r/<sha256(表示标签)>`（和本地缓存同样的键，表示标签里含哈希、尺寸、是否正方形、质量）。
- **账本**：Rust 自己的一张表 `sonus_r2_object`（不动 Navidrome 的表，原则 3）：对象键、种类、对应的歌曲或图片、版本、大小、状态（待传、已传、待删）、上传时间、失败次数。只有账本里标了“已传”且版本和当前一致的，才会让客户端去 R2 取。
- **后台上传任务**（在服务器进程里，不另跑程序）：
  - 启动后、之后每隔一段时间（默认 15 分钟），把数据库和账本对一遍：新歌、变了的歌放进待传；删除了的歌标成待删（宽限 7 天后真正删除，防止扫描中途误删）。
  - **限速**：按主人定的上限上传（默认例如 2 MB/s），可以只在夜里传；一次只传一个文件。第一次全量上传 75 GB：按 2 MB/s 约 10.5 小时，按 1 MB/s 约 21 小时。
  - 大文件用分片上传（例如每片 16 MB）；中断后从账本记下的状态重来。设一条 R2 生命周期规则，自动清掉 1 天内没完成的分片上传（否则会一直计费）。
  - 上传前后核对大小（和 ETag/MD5，单片上传时）；失败退避重试，连续失败的不再自动重试，只在日志里报一次。
- **缩放封面**：家里第一次生成（或从缓存读到）客户端常用尺寸时，放进待传；不主动为所有封面生成所有尺寸。

## 客户端怎么从 R2 取

1. 客户端照旧请求家里的 `stream?id=…` 或 `getCoverArt?id=…`，照旧登录。
2. 家里的服务器照旧核对登录、核对这个用户能不能看到这首歌或这张图、决定要不要转码（第 2 部分的规则）。
3. **只有同时满足以下几条**，才回 `302 Found`，`Location` 是一个**短时有效的 R2 签名地址**：
   - 不需要转码（原始文件），或者是封面；
   - 账本里这个对象“已传”且是当前版本；
   - 最近一次 R2 健康检查通过（见下）；
   - 客户端**声明它能处理跳转**（请求里带 `sonusMirror=1`，新版客户端才带；老客户端和第三方客户端什么都不变）；
   - 客户端不在家庭网络里（客户端地址不在主人配置的家庭网段里；在家时走局域网更快）。主人也可以选“所有地方都用 R2”或“完全不用”。
4. 否则一切照旧，由家里直接发送。

签名地址的细节：
- 用 S3 的 SigV4 查询签名（R2 兼容 S3 接口），只允许 `GET` 这一个对象。签名里不包含客户端信息。
- **有效期**：音乐默认 1 小时（够播完、来回拖动进度；R2 用 HTTP Range 支持拖动），封面默认 1 小时。
- **为了缓存**：签名时间按整点对齐（同一小时内同一对象的地址相同），浏览器和客户端的图片缓存才能命中；代价是一个地址最多可用 2 小时。
- 签名地址是“持有即可访问”的：拿到地址的人在有效期内能下载这一个文件。这和现在 Navidrome 的分享链接、艺人图片链接性质相同，但范围更小（单个文件、会过期）。**地址只发给已登录且有权访问这首歌或这张图的用户**；日志里绝不写签名。
- `HEAD` 请求也可以同样跳转。`If-…` 条件和 `Range` 由 R2 自己处理（待在真实 R2 上确认它们和家里服务器的行为一致，尤其是 `Content-Type`）。
- 对象上传时设好 `Content-Type`（按 Navidrome 的类型表）和 `Cache-Control`（封面原图和缩放图：长期；音乐：长期，因为版本变了键就变）。

各客户端对跳转的处理（代码里查到的，**待实测**）：
- Android 用 OkHttp 播放和取图，默认会跟随跳转，包括从 http 跳到 https。
- Windows 把地址交给 Media Foundation（`MediaSource.CreateFromUri`），一般会跟随跳转；取封面的方式要再查。
- 网页版用 `<audio>` 和 `<img>`，浏览器会跟随跳转；不需要 R2 设置跨域（CORS），除非以后改成用 `fetch` 取文件。

## R2 不可用、文件还没传上去时

- **还没传上去或版本不对**：不跳转，家里直接发送。新歌在上传完成前一律由家里发送。
- **R2 不可用**：后台每分钟对一个固定的小测试对象做一次签名 `HEAD`；失败就立刻停止所有跳转，直到恢复。最坏情况是在检查间隔内跳转的请求失败。
- **客户端的兜底**：新版客户端如果跟随跳转后失败（网络错误、403、404），就用同一首歌的原地址再请求一次，并带 `sonusMirror=0`，由家里直接发送。所以 R2 出问题时，用户最多感觉到一次重试的延迟。
- **对象在 R2 上被手动删了**：同上，客户端兜底；后台核对时（每天一次对账：列出 R2 上的对象和账本比较）把它重新标成待传。

## 费用（按 2026 年公布价格估算，动手前再核对）

| 项目 | 价格 | 估算 |
|---|---|---|
| 存储 | 每月每 GB 0.015 美元，前 10 GB 免费 | 约 75 GB：每月约 1 美元；全量 91 GB：约 1.2 美元 |
| A 类操作（写入、列举） | 每月前 100 万次免费，之后每百万次 4.5 美元 | 首次上传几千次、分片也就几万次；每天对账一次列举：远低于免费额度 |
| B 类操作（读取） | 每月前 1000 万次免费，之后每百万次 0.36 美元 | 每次播放几次 Range 读取、浏览封面几百次：远低于免费额度 |
| 流量（出口） | 免费 | 这是选 R2 的主要原因 |

会让费用失控的情况，以及对策：
- **反复重传**：版本键算错导致每次扫描都当成新文件。对策：版本只由 `updated_at` 和 `size` 决定；账本记录每天上传的字节数，超过上限（默认每天 20 GB）就暂停并在日志里报警。
- **未完成的分片上传**一直计费：生命周期规则自动清理。
- **签名地址被大量转发、被反复下载**：读取次数便宜、流量免费，费用影响很小；但仍要设有效期，并只发给有权限的用户。
- 建议主人在 Cloudflare 账户里设一个**费用提醒**（例如每月超过 5 美元提醒），这只有主人能设。

## 密钥放在哪里

- 需要：R2 的 Account ID（用来拼接口地址 `https://<account id>.r2.cloudflarestorage.com`）、存储桶名，以及一对 **只对这一个存储桶有读写权限的 API 令牌**（Access Key ID 和 Secret Access Key）。不要用账户级的全局密钥。
- **只放在服务器的运行环境里**：Unraid 容器的环境变量（例如 `SONUS_R2_ACCESS_KEY_ID`、`SONUS_R2_SECRET_ACCESS_KEY`），或者 `/data` 下一个只有服务器能读的文件（权限 0600）。**永远不放进代码仓库**，不出现在镜像里、不出现在 PR 里。
- 服务器程序里：密钥只在内存中；调试输出一律显示为“已设置”；日志绝不写密钥、签名或带签名的地址；出错信息里也会去掉。
- 存储桶设为**私有**：不开 r2.dev 公共地址，不绑定公开的自定义域名（访问全靠签名地址）。

## 安全要点（写代码时会进 `server/SECURITY.md`）

- 跳转前的检查和现在直接发送完全一样：先登录、再查权限，看不到的歌回“找不到”，不会给出签名地址。
- 签名只针对单个对象、只允许 GET、会过期；签名地址不含用户名或密码。
- 对象键不透露歌名、路径或用户。
- 上传只读家里已经在用的文件（同样的路径检查：只用数据库里的相对路径、必须在媒体库文件夹里），不接受客户端给的任何路径。
- 需要一个新的依赖：服务器现在只会发 HTTP，访问 R2 要 HTTPS，所以要加 TLS 客户端（计划用 `rustls`，纯 Rust；或 `hyper-rustls`）。SigV4 签名自己写（已有 `hmac`、`sha2`），用 AWS 公布的标准测试向量验证；不引入庞大的 AWS SDK。

## 不用真实 R2 怎么开发和测试

- **签名**：用 AWS 文档里公布的 SigV4 示例（固定的密钥、时间、请求，已知正确的签名）做单元测试，保证签名算法本身正确，不依赖我们自己的实现来“自证”。
- **上传和跳转**：测试里起一个**自己写的假 S3 服务**（本机 127.0.0.1，内存存储，接收 PUT、分片上传、GET、HEAD、列举，并按同样的 SigV4 规则核对签名、核对过期），测账本、限速、重试、健康检查、跳转、各种“不跳转”的情况。
- **也可以用 MinIO**（真正兼容 S3 的开源服务）做一次额外的核对；它需要另外下载，**要先问主人**。
- **只能在真实 R2 上确认的**：
  - 真实的签名地址在 R2 上能否用；
  - R2 对 `Range`、`If-…`、`Content-Type` 的处理；
  - 分片上传的限制；
  - 三个客户端在真实网络下跟随跳转、拖动进度、失败后兜底；
  - 上传速度对家里网络的实际影响；
  - 一个月后的实际账单。

## 分几步做

1. **R2-a**（不需要主人的密钥）：SigV4 签名（含标准测试向量）、TLS 客户端、配置项（默认关闭）、账本表、后台上传任务、健康检查、假 S3 测试。配置不填密钥时，整个功能不启动，行为和现在完全一样。
2. **R2-b**（不需要主人的密钥）：`stream` 和 `getCoverArt` 的跳转（只对带 `sonusMirror=1` 的请求），家庭网段判断，日志里不写签名。
3. **客户端**（由负责客户端的会话做）：Windows、Android、网页版在请求里带 `sonusMirror=1`，跟随跳转，失败时用 `sonusMirror=0` 重试。
4. **上线**（需要主人）：主人建存储桶和令牌、填进 Unraid 的环境变量、设费用提醒；先只开上传、观察几天的速度和账单，再开跳转。
