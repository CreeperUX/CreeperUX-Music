# Sonus 服务器 Rust 化路线图

2026-11-24 定稿，决定见文末（前五个当天定，第 6 个 2026-11-25 定）。依据：对冻结的 Navidrome 改版（`CreeperUX/navidrome`，0.64.2）和 Sonus 两个仓库的通读，分六块：Subsonic 接口层、数据层、入库（扫描、标签、封面、歌词）、播放与外部服务、网页与平台、Sonus 实际用到的接口。代码量都指非测试的 Go 代码行数。

## 目标与原则

目标：用 Rust 写的 Sonus 服务器逐步替换 Navidrome，最后镜像里不再有 Navidrome；同时换掉 Navidrome 的 React 网页界面。

1. **每一步都能上线、能回退。** Rust 网关始终挡在最前面，接管一个接口就上线一个；出了问题，把那个接口切回 Go 即可。
2. **按“状态”成组搬，不按单个接口搬。** Go 内存里有几块状态，相关的接口必须一起搬，否则两边各拿一半：
   - 正在播放（`scrobble`、`reportPlayback`、`getNowPlaying`）；
   - 网页的事件通道 SSE（收藏、评分、扫描进度会往里发事件）；
   - Connect 的设备表；
   - 浏览器登录里等待中的请求；
   - 登录失败限流、转码并发计数。
3. **数据库在 Go 退役前归 Go 管。** 表结构冻结在 goose 版本 `20260922230428`，加上 `sonus_*` 三张表。
   - Rust 启动时核对这个版本，不对就拒绝启动。
   - Rust 只做增量：新表放在自己的命名空间，用自己的版本表；不改、不重建 Go 的表。
   - 扫描器搬到 Rust 之后，才把表结构的管理权移交给 Rust。
4. **兼容性靠测试，不靠细心。** 三类测试：
   - Sonus 自己的客户端测试：单元测试、验收、`check-web`，能指向任意服务器；
   - 差分测试：同一批请求分别发给 Go 和 Rust，两边用同一份数据库副本，比较规整后的回复；
   - 从 Go 测试里抄出来的“金标准”用例：转码决策、ffmpeg 参数、智能歌单 SQL、搜索语法、ID 算法、标签解析等。
5. **只做 Sonus 要的**（决定 1）：不做“通用 Subsonic 服务器”。Go 退役之前，Rust 没接管的请求都由网关转给 Go，所以第三方客户端在过渡期照常能用；Go 退役之后就不再保证。

## 现状：Navidrome 有多大，哪些要搬

| 模块 | Go 代码量 | 关键依赖与难点 | Rust 难度 | 打算 |
|---|---|---|---|---|
| Subsonic 接口层 | 5.6k，66 个接口 | XML 和 JSON 两种格式省略字段的规则不同；兼容老客户端的模式 | M；连同背后的查询是 L | 先做 Sonus 用的约 22 个，只做 JSON |
| 数据层 | 约 11k（含智能歌单 1k），131 个迁移 | SQLite（WAL）、FTS5 搜索、自定义函数 `SEEDEDRAND`、时间戳格式、ID 编码 | 读和用户写是 L；连同扫描写入是 XL | 表结构由 Go 管到最后 |
| 入库：扫描、标签、封面、歌词 | 约 15–17k | 读标签用编译成 WASM 的 TagLib；专辑和艺人 ID 由标签算出 | XL | 最后搬 |
| 播放、转码、scrobble、外部服务、分享 | 约 13–14k | ffmpeg、转码缓存、播放器设置、Last.fm/ListenBrainz/Deezer | L；去掉点歌机等之后是 M | 中后期 |
| 网页、鉴权、配置、启动 | 约 10k | 密码可逆加密、JWT（滑动续期、epoch 吊销）、约 180 个配置项 | 平台部分 M，网页管理接口 L | 鉴权早搬；管理接口随新界面重做 |
| Sonus 自己加的 | Connect 0.55k，二步验证 1k，浏览器登录 0.3k | 浏览器登录的等待队列、二步验证的网页流程 | S–M | 最先搬 |
| 不搬 | 插件 25k（运行时 11k）、Jellyfin 5.1k、点歌机 1.1k、统计 0.8k | — | — | 直接砍掉 |

要重写的 Go 代码约 55–60k 行。网页界面另算：React 界面约 34k 行，整体换成新界面。

**Sonus 客户端实际用到的**：Subsonic 方法 22 个，加上 Connect 的 WebSocket、浏览器登录的 3 个接口和允许页的 3 个接口。全部用 JSON，不用 XML，不用 Navidrome 的 `/api`。没用到的：`estimateContentLength`、`timeOffset`、`getTranscodeDecision`、下载、分享、点歌机。

## 阶段

### 阶段 0：网关，行为不变（S–M）

- **网关本身**（`server/`，已完成，PR #2，细节见 `server/README.md`）：
  - 原样转发所有请求，流式双向传输，支持 WebSocket；
  - 自己判断客户端 IP，剥掉客户端伪造的转发头和 `Remote-User` 头；判断规则与 Navidrome 逐条对齐；
  - 负责启动和看护 Navidrome：把地址、端口、只信任网关、用户头名告诉它；没有可信代理时，用户头名每次启动随机生成；
  - 和 Navidrome 一样读配置：`ND_CONFIGFILE`（默认 `/data/navidrome.toml`）、`ND_*` 环境变量、命令行，优先级相同；`BaseURL` 的路径记下备用；
  - 会让 Navidrome 绕过网关的设置（TLS、命令行里的端口和地址等）直接拒绝启动；
  - 有单元测试和集成测试；冻结版 Navidrome 已在本机放到网关后面实测通过（网页登录、事件流、Subsonic、Range 串流、Connect、客户端 IP）。
- **测试**：
  - 演示服务器的测试和验收测试能指向外部地址（演示服务器已经搬到 `tools/demo-server/`）；
  - 写差分测试工具：请求清单 → 两边各发一次 → 规整 → 比较；
  - 准备一套固定的测试曲库和对应的数据库。
- **镜像与 CI**：`ghcr.io/creeperux/sonus-server`，在冻结版 Navidrome 镜像上加入 Rust 程序。Unraid 换成新镜像；回退就是换回旧镜像。
  - `server/Dockerfile` 和 `.github/workflows/server.yml` 已写好：每次改动跑格式、代码检查和测试；合并到 `main` 后、每周一 02:30 UTC 构建 amd64 和 arm64 两种镜像。
  - 本机没有 Docker，镜像要等合并后由 CI 第一次构建。
- **完成标准**：Sonus 的全部测试经过网关通过；正式服务器在网关后面平稳运行一两周。

### 阶段 1：Sonus 自己的部分（M）

服务器这一半已完成（2026-11-24）：Rust 服务器回答 `rest/connect?protocol=2`，做了什么、和参考实现有哪些已知差异、测了什么，见 `server/README.md` 的“Sonus Connect version 2”；安全上的决定见 `server/SECURITY.md`。

- **Connect 第 2 版：Spotify 式的播放会话**（2026-11-24 定）。不移植第 1 版，在 Rust 里直接实现第 2 版。规则：
  1. 一个账号同时只有一台设备出声。
  2. 每台设备一打开就显示正在哪台放什么，进度实时走。
  3. 在任何一台点歌、加队列、切歌、拖进度、随机/循环，都作用于正在出声的那台。
  4. 只能在设备列表里换出声设备；原来那台停下，变成遥控器。
  5. 队列只有一份，所有设备共用。
  6. 都关掉后，会话留在服务器上；哪台按播放，就从原处接着放。这一条取代“接着上次听”的提示。
  7. 出声设备掉线，会话停在原位。
  8. 音量属于每台设备自己。
- **怎么推进**：
  - 协议先写成文档：`docs/protocol/connect.md`。
  - 演示服务器和 Windows 客户端先按新协议改。这一步不依赖网关，可以和阶段 0 并行，但要等“客户端测试改造”合并之后再开始，因为两边都要改验收测试。
  - 服务器那一半在网关里实现，会话保存在数据库里，关机重启后仍在。（已完成）
    - 会话逻辑照着参考实现（`tools/demo-server/connect-session.mjs`）逐句移植，不含时钟、随机数和网络；共用的测试向量（`docs/protocol/connect-vectors.json`，14 个用例、157 步）逐步回放，结果完全一致。
    - 会话存在 Rust 自己的表 `sonus_connect_session` 里，版本记在 Rust 自己的版本表 `sonus_server_schema` 里；都放在 Navidrome 的数据库文件中，只新增、不改 Go 的表。变化后一秒内写入，关机时再写一次；重启后会话还在，没有出声设备，停在原位置。
    - 歌曲信息（标题、时长、是否存在）只读 Navidrome 的曲库表，按这个用户看得到的范围来。
    - 实测：带着这两张新表，冻结版 Navidrome 照常启动和运行。
  - 身份由 Rust 自己判断（阶段 2 先完成了，所以没有走“先交给 Go”的过渡）：和其他 Subsonic 请求用同一套校验和同一个失败限流；没登录就没有会话。
  - 网页版这时第一次加上 Connect。
  - Go 的第 1 版在所有客户端都换到新版之前继续保留：不带 `protocol=2` 的请求照旧转给 Go。
  - Windows 客户端已对着 Rust 服务器实测：两台静默的程序实例共用一个账号，验收的登录和 Connect 两轮 20 项全部通过（1 项跳过：要靠演示服务器的测试钩子单独切断一台设备）。
  - 还没做的：Android 客户端对着 Rust 服务器的实测；正式服务器换上新镜像。
- **扩展列表**：`getOpenSubsonicExtensions` 由网关合并 Go 和 Rust 两边的列表。（已完成：`sonusConnect` 的版本现在是 `[1, 2]`；回复的其余部分和格式保持 Go 的原样，JSON、JSONP、XML 都是。）
- **请求体上限**：搬到网关（已在阶段 2 完成）。

### 阶段 2：身份与鉴权（M）

已完成（2026-11-24）：数据库基础和 Subsonic 鉴权在 PR #6，`/auth/*` 在随后的 PR；做了什么、和 Go 有哪些已知差异、测了什么，见 `server/README.md`；安全上的决定和信任边界见 `server/SECURITY.md`。

- **数据库基础**（已完成，PR #6）：
  - 连接设置：WAL、`busy_timeout` 15 秒、所有写事务都用 `BEGIN IMMEDIATE`、事务尽量短、永远不 VACUUM；
  - 启动时核对表结构版本；
  - ID 和时间戳的编解码；
  - 密码和密钥解密：AES-GCM，密钥由 `PasswordEncryptionKey` 推出。
- **Subsonic 鉴权**（已完成，PR #6）：
  - 支持 `u`+`p`/`enc:`、`t`/`s`、`apiKey`（错误 43/44）、应用专用密码，以及“开了二步验证就必须用应用专用密码”的规则；
  - 登录失败限流；`tokenInfo`；
  - 鉴权通过后，用网关自己的身份头告诉 Go 是谁（Go 只信任 127.0.0.1），并把凭据从请求里剥掉。
  - 实际做法比原计划多一点：XML、JSONP 和所有 HTTP 方法也由 Rust 判定，这样比对密码的地方只有一处、限流只有一份。
- **`/auth/*` 整组搬过来**（已完成）：登录、首个管理员、二步验证、应用专用密码、浏览器登录（6 个接口）。签发的 JWT 与 Go 的完全一致：同一个密钥，字段 `uid`/`adm`/`ep`/`aud`。这样旧的 React 界面照常能用。
  - `/auth` 下的所有路径都由 Rust 回答（不认识的路径回 404/405），只有 CORS 预检交给 Go。
  - 浏览器登录里等待中的请求现在存在 Rust 的内存里。
  - 按来源地址的限流、`/auth` 的 8 KB 请求体上限、`/api` 的 4 MiB 请求体上限都搬到了网关（阶段 1 里“请求体上限”一项随之完成）。
  - 启动时 Rust 会向 Go 发一次必然失败的登录探测，让 Go 先把密码加密的密钥定下来；否则在新库上由 Rust 创建的首个管理员，Go 会读不出密码。
- **完成标准**（已达到）：鉴权的黑盒测试，加上从 Go 测试里抄来的用例，全部通过；旧 React 界面经无头浏览器检查可用；Rust 和 Go 签发的令牌互相认可。
- **还归 Go 的**：`/api`（含用户管理和改密码）、令牌的滑动续期、带 `jwt=` 的 Subsonic 请求、Jellyfin 接口自己的登录。

### 阶段 3：曲库读取（L）

三个部分都已完成（2026-11-25）。第 1 部分：响应的基础（Go 的 JSON 写法、专辑和歌曲的字段、按用户的收藏和播放数据、每个用户能看到的范围、会改变输出的配置项），以及 `ping`、`getSong`、`getAlbum`、`getAlbumList2` 四个接口。第 2 部分：`search3`（空查询按表的顺序分页，客户端靠它同步整个曲库；文字查询走 FTS5，查询的构造和排序照 Navidrome 移植；中日韩文字走 LIKE；MusicBrainz ID 直接按 ID 查）、`getStarred2`、`getPlaylists`、`getPlaylist`、`getPlayQueue`。第 3 部分：`getLyricsBySongId`（数据库里存的内嵌歌词）和 `getCoverArt` 的读取部分。做了什么、哪些请求仍交给 Go 及原因、测了什么，见 `server/README.md` 的 “The library's reads”；安全上的说明见 `server/SECURITY.md`。

- **已定的做法**（第 1 部分）：
  - **只做 JSON**：要 XML 或 JSONP 的请求照旧交给 Go（已由网关核对过登录）。
  - **拿不准就交给 Go**：Sonus 客户端不发的参数（`musicFolderId`）、设了强制转码的播放器、Go 要向操作系统查询类型的文件后缀、Rust 读法可能与 Go 不同的数据行、读库出错，一律原样转给 Go，不做近似。
  - **播放器登记仍归 Go**（到阶段 4 再搬）：Rust 回答一个请求前，先以该用户的身份向 Go 发一次 `ping`，带上客户端名、Cookie、`User-Agent` 和客户端地址，由 Go 按自己的规则找到或新建播放器，Rust 把 Go 回的 Cookie 原样交给客户端。结果每个客户端每分钟记一次（Go 自己也是每分钟最多写一次播放器），播放器的设置（如 `ReportRealPath`）每次请求都重新读库。所以 Go 的日志里，一个客户端的读取只表现为每分钟一次 `ping`。
  - **最后访问时间**：Rust 回答的请求由 Rust 写，频率和 Go 一样（每个用户每分钟最多一次）。
  - **随机专辑列表**：种子存在 Rust 的内存里，规则和 Go 一样（从头取就换一个新顺序，同一轮翻页彼此衔接）；顺序本身和 Go 的不同（两边都是随机）。
  - **证明是 Rust 回答的**：调试版在回复里加 `X-Sonus-Answered: rust` 头，差分工具逐条核对；正式镜像不带这个头。
- **第 2 部分定下的做法**：
  - **智能歌单先交给 Go**（上面两种做法里的第一种）：读取一个智能歌单时 Go 可能重新填充它，这是一次写入；`getPlaylist` 遇到智能歌单就原样转给 Go。歌单列表（`getPlaylists`）里的智能歌单由 Rust 按上次填充的结果列出，Go 在这里本来也不刷新。
  - **带图片的艺人交给 Go**：这样的艺人在回复里带一个由 Go 签名的公开图片链接（`artistImageUrl`），签名用的密钥 Rust 不读。所以 `search3` 或 `getStarred2` 的结果里只要有带图片（或图片还没处理完）的艺人，整条请求转给 Go。客户端同步曲库用的空查询不要艺人（`artistCount=0`），不受影响。
  - **旧式搜索交给 Go**：配置了 `Search.Backend=legacy` 或 `Search.FullString` 时，`search3` 转给 Go。
  - **艺人图片链接不做**（2026-11-25 定）：三个 Sonus 客户端都不读 `artistImageUrl`，Rust 不去读签名用的密钥；Go 退役时这个字段一并取消。
- **第 3 部分定下的做法**：
  - **`getScanStatus` 仍归 Go**：扫描是否在进行、进度多少，都在 Go 的内存里，数据库里读不到同样的东西。等扫描器搬到 Rust（阶段 7）时再接管。
  - **歌词**：只回答数据库里存的内嵌歌词。歌曲旁边有歌词文件（`.lrc` 等，按 `LyricsPriority` 排在“内嵌”之前）时，Go 每次请求都要读并解析这个文件，这类歌曲转给 Go。Rust 只看文件在不在，不读它。
  - **封面**：只在 Go 已经确定了这张图（数据库里有它的状态和哈希）、而且图片就在状态所指的位置时由 Rust 提供：原图来自文件夹里的封面文件（修改时间必须和 Go 记下的一致）或 Go 的图片仓库；缩放后的图只从 Go 的缩放缓存里读，Go 没缩放过的尺寸第一次仍由 Go 生成，之后由 Rust 提供。碟片封面（`dc-…`，每次要在文件夹里找）、还没有状态的图、没有图片的条目（占位图）都转给 Go。缩放本身和缓存的管理留到阶段 5。
  - **测试环境**：标准数据库现在连同 Go 的图片仓库一起保存和复制，构建时让 Go 把每个歌单的封面都定下来；副本里的封面不再依赖后台处理的时机（第 2 部分偶发过一次的差异就是这个原因：智能歌单的封面在每次启动几秒后才生成）。
- **实测**（冻结版 Navidrome 0.64.2-sonus.10）：差分 443 条请求全部一致，其中 329 条由 Rust 自己回答（搜索语法的移植通过了 Navidrome 自带测试的全部用例；封面的字节和缓存相关的响应头逐项相同）；契约测试 131 项全过；把 Go 的日志开到 debug，被接管的请求在 Go 的日志里没有任何痕迹，只有一次登记用的 `ping`。
- **Windows 客户端验收**（对着 Rust 服务器，53 首歌的生成曲库）：14 轮 92 项全部通过，4 项跳过（曲库里没有 DSD；大封面在前几轮已取过；两项 Connect 检查只适用于第 1 版或演示服务器）。期间 Rust 自己回答了 317 个曲库请求，另有 29 个按上面的规则转给 Go（23 个第一次缩放的封面、4 个碟片封面、2 首带歌词文件的歌）。
- **正式数据库副本上的差分**（2026-11-25，阶段 3 的最后一项检查）：在正式数据库的两份副本上（2379 首歌、877 张专辑、594 位艺人、17 个歌单、3 位用户；音乐文件和图片不在这台电脑上），用从数据本身生成的 9638 个请求（每位用户一份）对比 Go 和 Rust：**9638 个全部一致**。其中 9504 个由 Rust 自己回答，134 个转给 Go：102 个搜索的结果里有带图片的艺人（594 位艺人里 340 位有图片），32 个封面（图片文件不在这台电脑上，两边都由 Go 回答，结果相同）。客户端同步曲库用的请求（专辑列表、空查询的歌曲分页）全部由 Rust 回答。第一次对比有 29 个不同，全是歌曲参与者（`contributors`）的顺序：Go 按 map 遍历角色，顺序每次随机，两个 Go 之间也会不同，所以改为不计顺序比较，不是 Rust 的错误。耗时（中位数，Rust 发布版对 Go）：`getAlbum` 1.1 对 2.7 毫秒，`getSong` 0.8 对 1.7，`search3` 9.4 对 13.4，`getAlbumList2` 1.8 对 3.6；Go 在这台 ARM 电脑上是模拟运行的 x86-64 版，比较只供参考。工具：`tools/contract/corpus-from-db.mjs` 和 `diff.mjs --db`，副本用完即删，原文件没有改动。
- **还没做的**：Android 和网页客户端对着 Rust 服务器的实测。
- **要接管的接口**：`ping`、`getScanStatus`、`getAlbumList2`、`getAlbum`、`getSong`、`search3`、`getPlaylists`/`getPlaylist`、`getPlayQueue`、`getStarred2`、`getLyricsBySongId`，以及 `getCoverArt` 的读取部分（Rust 没命中时交回 Go）。
- **`search3`**：既要支持空查询分页（客户端靠它同步整个曲库），也要移植 FTS5 搜索。
- **智能歌单**：两种做法。
  - 先交给 Go：网关把智能歌单的请求转给 Go。
  - 或者把条件 → SQL 的翻译也移植过来：Go 有 94 条断言精确 SQL 的测试可以对照。
- **验证**：在正式数据库的副本上做差分测试（已完成，见上面的结果）。

### 阶段 4：用户写入与播放状态（M–L）

- **收藏、评分、歌单增删改、保存播放队列**：
  - 写法要和 Go 一致：更新不到就插入；收藏时间；平均评分重算。
  - 旧 React 界面靠 Go 的 SSE 收到这些变化。两个办法：接受旧界面不自动刷新，或者在 Go 里加一个小钩子。
- **正在播放**：`scrobble`、`reportPlayback`、`getNowPlaying` 一起搬。
  - 播放次数的事务：歌曲、专辑、每位艺人同时加一。
  - 播放器登记：沿用同一个 Cookie 和匹配规则，否则播放器上的转码设置会丢。
- **不再往外发播放记录**（决定 3）：Rust 接管 `scrobble` 时不做 Last.fm/ListenBrainz 的发送。从那时起，Go 那边配置过的外部 scrobble 也一起停止。（第 3 部分已做到，见下。）
- **第 1 部分：收藏、评分、播放队列**（2026-11-25）：`star`、`unstar`、`setRating`、`savePlayQueue` 由 Rust 回答，写法和 Go 一致。
  - 收藏：更新不到就插入；取消收藏也写收藏时间；查找条目的规则和 Go 一样（艺人、专辑、歌单、歌曲、电台，按用户能看到的范围），看不到的跳过。
  - 评分：写评分和评分时间，再按所有用户大于 0 的评分重算平均分（保留两位小数）。
  - 播放队列：整条替换；再次保存时沿用原来的 id，创建时间按 Go 的做法写成零时间；不带歌曲就是清空。
  - 时间格式和 Go 写入的一样，用服务器所在时区。
  - **Go 不缓存这些表**（已查：它只缓存媒体库路径），所以一边写了另一边马上能读到，测试两个方向都验证过（包括旧网页界面用的 `/api`）。
  - **旧网页界面不会自动刷新**：Go 收藏或评分时会推送 `refreshResource` 事件，Rust 写入时不推（决定 2），刷新页面后可见。
  - **实测**：写入请求集 84 条回复全部一致（76 条由 Rust 回答），跑完后两边数据库逐表逐行一致；在正式数据库的两份副本上，用真实数据生成的 173 条写入请求全部一致（167 条由 Rust 回答，6 条因结果里有带图片的艺人交给 Go），两边数据库一致（750 行收藏和评分记录）；两位用户同时写入 128 条、再同时取消收藏 26 条，一条不丢；别的程序占着写锁 4 秒、Go 全量扫描期间写入 120 条，全部成功。
  - 第一次对比时有一处差异，可以接受：Go 在 Windows 上时钟精度粗，同一次请求里收藏的几项常拿到完全相同的时间，`getStarred2` 里的先后就不固定；在 Linux 上不会这样。
- **第 2 部分：歌单**（2026-11-25）：`createPlaylist`（新建，以及带 `playlistId` 时替换歌曲）、`updatePlaylist`、`deletePlaylist` 由 Rust 回答，写法和 Go 一致。
  - 权限：只能改自己的歌单（管理员可以改所有人的）；看不到的歌单回“找不到”（70），看得到但不是自己的回 50；和文件同步的歌单不能改歌曲。
  - 歌曲：用户读不到的歌不加进去；去掉指定位置的歌以后重新从 1 编号，新加的接在最后；歌曲数、总时长、总大小按 Go 的算法重算。
  - 替换歌曲时没给歌，原来的歌保留（Go 就是这样）。
  - 封面：歌单的歌一变，就把它放进 Go 的封面队列，由 Go 的后台每 5 秒取一次重新生成。封面是从歌单的专辑里随机挑来拼的，所以两边生成的不一样，比对时只核对“重新生成过”。
  - **智能歌单仍归 Go**；删除带自定义封面的歌单也交给 Go（它要删图片文件）。
  - **实测**：写入请求集 132 条回复全部一致（127 条由 Rust 回答），两边数据库逐表逐行一致；在正式数据库的两份副本上，用真实数据生成的 205 条写入请求（含真实歌单的修改、替换、删除）全部一致，两边数据库一致（20 个歌单、1382 行歌单曲目）；同时往一个歌单追加 60 首、另一位用户同时往自己的歌单加歌，全部保留，编号没有空缺或重复。
- **第 3 部分：播放记录和“正在播放”**（2026-11-25）：`scrobble`、`reportPlayback`、`getNowPlaying` 由 Rust 回答。
  - 播放记录：歌曲、专辑和歌曲的每位艺人的播放次数各加一，最后播放时间取较晚的一次，另写一行播放历史（`scrobbles`），都和 Go 写法一样；用户看不到的歌跳过。
  - “正在播放”是 Go 内存里的第一块状态，现在整块搬到 Rust（原则 2）：`scrobble` 的“正在播放”、`reportPlayback`、`getNowPlaying` 一起搬。过期规则和 Go 一样：歌曲剩下的时长再加 5 秒，暂停 30 分钟。服务器重启后“正在播放”清空，和 Go 一样。
  - **`reportPlayback` 也搬了**：Sonus 客户端不发它，但 Go 自带的旧网页界面播放时用它报告；如果留在 Go，旧界面的“正在播放”面板（它通过 `getNowPlaying` 读列表）会看不到网页里正在播放的内容。停止时播放超过一半（最多 4 分钟）才计一次，和 Go 一样。
  - **不再往外发播放记录**（决定 3）：Go 从此看不到任何播放，所以不会再往 Last.fm、ListenBrainz 或插件发送；测试核对了 Go 的调试日志和它的待发缓冲表，都没有痕迹（对照组：Go 自己收到的播放会出现在日志里）。
  - **旧网页界面**：右上角“正在播放”的数字由 Go 通过事件推送，Go 现在没有会话，所以这个数字不再自动变化；点开面板时它会向 Rust 要列表，显示正确的内容和数量（决定 2）。
  - **播放器登记仍归 Go**：搬过来要照搬 Go 找到或新建播放器的规则、Cookie 和每分钟一次的写入，而客户端看不出任何区别；旧网页界面还在通过 `/api` 编辑播放器，串流（阶段 5）也还在 Go 那里读播放器。写入只需要播放器的 id 和“是否计播放”，都从 Go 维护的那一行读。等阶段 5 串流搬过来时再一起搬。
  - **实测**：写入请求集 187 条回复全部一致（185 条由 Rust 回答），两边数据库逐表逐行一致（含播放历史）；“正在播放”的各种状态、乱序报告、到时消失都和 Go 一致；在正式数据库的两份副本上，用真实数据生成的 250 条写入请求（含播放记录、播放报告、正在播放）全部一致，两边数据库一致（2332 行播放历史）。
- **阶段 4 结束时的 Windows 客户端验收**（对着 Rust 服务器，全新的 53 首歌生成曲库）：14 轮 92 项全部通过，4 项跳过（和阶段 3 结束时同样的 4 项）。期间 Rust 自己回答了 348 个曲库请求（其中写入：22 次 `scrobble`、4 次建歌单、4 次删歌单、3 次改歌单、收藏和取消收藏各 1 次），另有 29 个按已写明的规则交给 Go（23 个第一次缩放的封面、4 个碟片封面、2 首带歌词文件的歌）；Go 的外部播放记录待发缓冲一直是空的。

### 阶段 5：媒体传输（M–L）

- **原始文件串流**：`Range`、`HEAD`、`If-*` 全部支持。
- **转码**：
  - 移植转码决策，Go 有 71 + 37 个金标准用例；
  - 只保留内置的 4 种格式（mp3、opus、aac、flac），不支持自定义命令模板；
  - 转码缓存用自己的文件夹；
  - FLAC 头的修补要照做。
- **封面**：缩放、占位色，以及后台的封面处理队列（`artwork_queue` 是现成的分界点）。
- **打包下载**：用到再做。
- **音乐文件和封面镜像到 Cloudflare R2**（2026-11-25 定，决定 6）：
  - NAS 上的文件仍是原件；文件同步到一个私有的 R2 存储桶。
  - 原始文件的 `stream` 和 `getCoverArt`：Rust 服务器先核对登录，再把请求重定向到一个短时有效的 R2 签名地址。
  - 需要转码的歌、还没同步上去的歌，仍由服务器自己传。
  - 可选：只对家庭网络之外的客户端这样做。
  - 目的：在国外访问更快，少依赖家里的上行带宽。

### 阶段 6：新网页界面和 Sonus 管理接口（L，可与阶段 3–5 并行）

- **管理接口**：设计 `/sonus/v1`，覆盖用户、媒体库、播放器、歌单、扫描控制、缺失文件、设置和事件通道。用明确的类型和分页，取代 react-admin 的通用增删改查。
- **新界面**：放在 `web/` 里继续做，浏览和播放走 Subsonic，管理走 `/sonus/v1`。允许页和二步验证的网页流程也移到新界面。
- **完成标准**：新界面能替代旧界面之后，React 界面和 Navidrome 的 `/api` 一起退役。

### 阶段 7：入库（XL，最难，最后做）

- **读标签**：先确定用什么读（见下方“要你定的事”），再用 Rust 写出从文件到曲目记录的转换。
- **验证**：在你的真实曲库上，和 Go 的结果逐行比对。**ID 必须完全一致**，否则收藏、播放次数和歌单会对不上、悄悄丢失。
- **扫描器**：分阶段处理、文件夹监视、清理、统计、歌单导入。
- **切换**：关掉 Go 的扫描器（`Scanner.Enabled=false`），由网关接管 `startScan` 和 `getScanStatus`。
- **移交**：表结构的管理权交给 Rust，以冻结时的结构为起点，之后用 Rust 自己的迁移。

### 阶段 8：Go 退役（M）

- **剩下的接口**：
  - 艺人简介和图片（`getArtistInfo2`）：移植，数据来自 Deezer（不需要密钥）。
  - 相似歌曲和热门歌曲：改为按自己的曲库推算（决定 3）。
  - Sonus 不用的其他接口：随 Go 一起下线（决定 1）。
- **镜像**：不再包含 Navidrome。
- **统一格式**：时间戳统一成 UTC 的一种格式；清掉为兼容 Go 而保留的列。

## 横跨各阶段的风险

- **两个进程写同一个 SQLite**：Go 的接口、Go 的扫描子进程和 Rust 同时写。照阶段 2 的连接规则来；扫描期间写入会排队等待。
- **Rust 依赖 SQLite 的两个功能**：Rust 必须带 FTS5 和 JSON1。没有 FTS5，任何写曲目、专辑、艺人表的操作都会因触发器而失败。阶段 0 先确认 rusqlite 自带的 SQLite 包含 FTS5。
- **逐字节一致**：时间戳格式（Go 的写法是 `2006-01-02 15:04:05.999999999-07:00`，按字符串比较）、ID 编码、排序规则、搜索语法。都靠差分测试兜住。
- **Go 的缓存**：Go 可能缓存了 Rust 会写的表，这一点还没确认。阶段 3 只读不写（除了最后访问时间，Go 不缓存它），所以推迟到阶段 4 前查清。
- **许可证**：照着 Navidrome 逻辑移植的 Rust 代码，属于 Navidrome（GPL-3.0）的衍生作品。
  - GPL-3.0 和 AGPL-3.0 允许合在一起（两份许可证的第 13 条），但这类文件要保留 Navidrome 的版权说明。
  - 只参考协议文档、从头写的部分不受此限。

## 已定的决定（2026-11-24；决定 6：2026-11-25）

1. **只支持 Sonus 自己的客户端。**
   - Rust 只做 Sonus 用到的 22 个 Subsonic 方法，只做 JSON，再加上 Connect 和浏览器登录。
   - 不做 XML、JSONP、兼容老客户端的模式，也不做 Sonus 不用的接口：分享、电台、书签、打包下载、`getArtists`/`getIndexes` 等。
   - 第三方 App 在 Go 退役前照常能用，之后不再保证。
2. **旧 React 界面一直用到新界面做好。**
   - Rust 接管登录后，签发的 JWT 要和 Go 的完全兼容：滑动续期、epoch 吊销。
   - `/api` 和网页的事件通道（SSE）一直交给 Go。
   - Rust 写入的收藏、歌单等变化，旧界面不会自动刷新，手动刷新即可，可以接受。
3. **外部服务只保留艺人简介和图片。**
   - 不往 Last.fm/ListenBrainz 发播放记录。
   - 相似歌曲和热门歌曲改为按自己的曲库推算。
   - 外部服务的连接（Last.fm/ListenBrainz 绑定）、外部歌曲和本地曲库的匹配都不移植。
4. **多用户，一个媒体库。**
   - 保留每个用户各自的收藏、播放次数、歌单和管理员权限。
   - 不做多媒体库：不做媒体库管理、按用户分配媒体库、跨媒体库搬移。
   - Rust 启动时确认库里只有一个媒体库，否则拒绝启动。
5. **读标签以纯 Rust 为基础。**
   - lofty 作为主力；lofty 不支持的格式（WMA/ASF、DSF、TAK），用自己写的小解析器补上标签和时长等属性。
   - 阶段 7 开始前，先只读统计正式曲库里各格式的数量，确定哪些必须补。
   - 再用真实曲库逐行比对 Go 的结果，确保 ID 不变。
6. **做 R2 镜像；云端节点暂不考虑**（2026-11-25）。
   - 音乐文件和封面镜像到 Cloudflare R2，做法见阶段 5。
   - 云端节点（服务器整体上云）暂不考虑。

## 砍掉清单

- **插件和兼容层**：插件系统、Jellyfin 兼容层（连同 QuickConnect 和局域网发现）。
- **服务器端播放和统计**：点歌机、匿名统计、Prometheus。
- **Sonus 不用的接口**：播客、视频和聊天，声学相似度（只靠插件实现）。
- **兼容第三方客户端的部分**（决定 1）：XML、JSONP、兼容老客户端的模式，以及 Sonus 不用的 Subsonic 接口。
- **外部服务**（决定 3）：外部 scrobble 及其缓冲队列，Last.fm/ListenBrainz 的账号绑定，外部歌曲和本地曲库的匹配。
- **多媒体库**（决定 4）。
- **转码和扫描的实现方式**：自定义转码命令模板、子进程扫描器。
- **配置**：只留 TOML 和环境变量。

## 通读时顺带发现的问题

- **网页版的歌词时间偏移正负号反了**（已确认）：`web/src/api/subsonic.js` 用的是 `start + offset`，Windows 版用 `start − offset`。按 OpenSubsonic，正的偏移应该让歌词提前，所以网页版错了。演示服务器的偏移总是 0，测试一直没发现。
- **改版：经反向代理外部认证登录的二步验证用户，网页仍会拿到由密码算出的 Subsonic 令牌**（已确认）：`server/auth.go` 的 `handleLoginFromHeaders` 没有调用 `withoutSubsonicToken`。只有启用了 `ExtAuth` 才会碰到。
- **待核实**：曲目持久 ID 的规则用了 `discnumber`/`tracknumber`，而标签映射里叫 `disc`/`track`，这两项可能永远是空的。Rust 必须照原样复现，不能顺手修掉。
- **网关骨架还缺读取 `navidrome.toml` 和 `BaseURL`**：已补上（PR #2）。补的时候还发现骨架有一处和 Navidrome 不一致：同一个 `X-Real-IP` 头出现两次时，骨架取第一个值，Navidrome 取最后一个；可信代理若是追加这个头，客户端就能伪造地址。也已改正。
